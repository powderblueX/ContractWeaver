# 模板推荐：检索、排序与评估

## 实际流程

明确点名优先于普通检索：分析 Agent 返回 `requested_templates`（原名、行号、逐字引用），服务器验证名称与引用确实存在于对应行；另扫描原文中“需要/采用/签订”等正向请求中的实际目录名称，避免 LLM 泛化或遗漏检索词。名称做 Unicode、空白和书名号归一化，不猜同义词。明确版本优先匹配该版本；只点名合同类型时可能展示多个版本供选择。

否定或问句不进入原文规则兜底，但规则不等于完整的会话共识解析；先要求后取消、多义简称、复杂转折仍需分析 Agent 和用户审核。精确名称不是业务适用性证明。若明确点名的模板被结构拦截，仍优先显示并说明原因，仅允许预览和下载，不允许绕过生成限制。普通非点名候选才按“可填写”过滤。

```text
协商记录 → LLM 分析交易与检索意图
    → 名称 BM25 + 业务关键词 BM25 + 可选向量召回
    → RRF 融合排序 → 检查前 30 个候选的填写安全性
    → 最多推荐 5 份可填写模板 → 用户选择或浏览完整模板库
```

名称和关键词分开建立轻量 BM25 分数，中文使用字符二元组，英文与数字按词处理。BM25 考虑词的稀有度、出现次数和文档长度，不再仅计算字符重合。`template_retrieval.py` 将各路**排名**通过加权 Reciprocal Rank Fusion 合并，不直接相加尺度不同的原始分数；名称权重 2、关键词 1、可选向量 1，完整名称匹配额外权重 2。RRF 的一般原理见 [Microsoft 官方说明](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)，本项目不依赖 Azure。

当前不另调用 LLM 重排，也不会把完整模板库发送给模型。默认只有本地 BM25；配置本地 MiniLM 模型及对应 FAISS 索引后才加入向量路。向量不可用时回退 BM25。这里是“为填写任务检索模板”，不是面向整库条款问答的完整 RAG。

精确点名结果置前，其余按融合排序；仅检查有界候选池，不为凑满五份扫描全库。结果可能少于五份甚至为空，多个点名版本超过上限时须自行浏览。点名但不可填写的原件也占推荐名额。展示分数是相对排序分而非适用概率，点名优先不等于分数较高，更不能宣称全库最优。用户始终可以独立浏览、预览和下载完整模板库；硬拦截不能通过手动选择绕开。

## 配置位置

在 `backend/.env` 调整，默认值见 `.env.example`：

```dotenv
LAW_RECOMMENDATION_LIMIT=5
LAW_RETRIEVAL_CANDIDATE_POOL=30
LAW_RETRIEVAL_BM25_K1=1.5
LAW_RETRIEVAL_BM25_B=0.75
LAW_RETRIEVAL_RRF_CONSTANT=60
```

路由依赖层将配置注入 `RetrievalPolicy`；排序算法、Word 安全检查和工作流保持独立。来源权重集中在该策略类中维护，不散落于路由。

## 更进一步的路线

更有价值的增量是：给原件维护可审核的合同类型、适用交易、主体角色、地区、版本、必要条件等元数据；加入经过中文合同评测的 embedding；召回后再用 cross-encoder 或受约束 LLM 重排并输出适用理由与排除条件。模型、索引和元数据必须版本对应，不能只替换模型后沿用旧向量。

这些是后续方案，不是当前已经实现或已被证明优于 BM25 的结果。先建立“协商记录 → 人工标注适用模板”的评测集，用 Recall@30、NDCG@5、用户选择率、延迟与费用比较；否则新增模型不能证明推荐更好。567 份模板规模下，当前轻量实现无需额外向量数据库，也不必把系统改成复杂的自主 Agent 网络。
